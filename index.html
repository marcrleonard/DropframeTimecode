Why drop frame exists

NTSC color video runs at 30000/1001 ≈ 29.97 frames per second, not 30. If you count those frames with plain 30 fps timecode, the clock on the wall pulls ahead of the timecode by about 3.6 seconds every hour. That's fine until someone needs a one-hour show to actually be one hour.

Drop frame fixes this by skipping frame numbers (never actual frames) so the timecode stays in step with real time. The picture is untouched; only the labels jump.

;00 ;01

At 29.97, the first 2 frame numbers of every minute are skipped.

;00 → ;03

At 59.94, the first 4 frame numbers of every minute are skipped.

×10

Except every 10th minute (00, 10, 20…), where nothing is skipped.

What it looks like at 29.97

minute 1 00:00:59;28 00:00:59;29 00:01:00;00 00:01:00;01 00:01:00;02
minute 10 00:09:59;28 00:09:59;29 00:10:00;00 00:10:00;01 00:10:00;02

The math: 2 numbers × 54 non-tenth minutes = 108 frame numbers dropped per hour, which is exactly the 3.6 seconds of drift. By convention, drop frame uses a semicolon (;) before the frames field and non-drop uses a colon (:).

TimecodeTool

Go · CLI · MIT

Need this in a script or pipeline? TimecodeTool is a small command-line tool (and Go library) from the same author. It validates timecodes, measures the span between two of them, and does timecode arithmetic, with JSON output so it fits neatly into automation. 

# Is this valid drop frame?
$ TimecodeTool validate "00:07:00;00" --fps=29.97

# Duration and frame count between two timecodes
$ TimecodeTool span "01:00:00:00" "01:01:00:00" --fps=23.98

# Add and subtract timecodes and raw frames
$ TimecodeTool calculate "01:00:00:00" + "00:00:01:00" + 23 - "00:00:00:10" --fps=23.98
  • validateCheck that a timecode is legal at a given frame rate, drop frame included.
  • spanPlayback duration and frame count between two timecodes, inclusive or exclusive.
  • calculateChain timecodes and frame counts with + and -.
